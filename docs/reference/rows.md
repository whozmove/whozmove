# What a row holds

Each session the panel lists reaches the page as one row, in `update(rows, now)`: a JSON object that
`app/Row.m` builds from five places. This page is the list of its fields. A field that's unknown is left out,
never sent as `null`. Times are milliseconds since 1970.

`Whozmove --print-rows` prints the rows for the home folder in `$HOME`. `tests/rows.sh` checks those against a
recorded copy, and checks that every field `app/Row.m` sends is described here, and nothing more.

Your plan's usage isn't in the rows: it's the panel's, not a session's, and reaches the page apart from them
(`setUsage`, see [the bridge](bridge.md)). The second or so that the Claude Code module runs `claude` to ask for it, Claude
Code lists that run in its registry like any session; it runs in a folder kept for it, and is never a row.

## From Claude Code's registry

`~/.claude/sessions/<pid>.json`: one file per running session, written by Claude Code. A conversation can run in more
than one process at once: resumed in a second tab while it still runs, or open in Claude Desktop and a terminal. It's
still one row, whose fields here are those of the copy that needs you most: one asking you something, then one at
work, and otherwise the one the row followed already (when the row is new, the one whose state changed last, then the
one started last). One paused in its terminal (Ctrl+Z) never speaks for it while another runs.

| Field | What it is |
|---|---|
| `sessionId` | Claude Code's id for the session |
| `hostSessionId` | for a session in Claude Desktop, the conversation's own id there (`local_…`) |
| `pid` | the session's process; 0 for a conversation with no process (a closed Claude Desktop conversation, or a terminal session that has ended) |
| `procStart` | when that process started; with `pid`, it tells a process from a later one given the same pid |
| `cwd` | the folder the session runs in |
| `name` | the session's name, if it was given one |
| `entrypoint` | `cli` for a terminal, `claude-desktop` for Claude Desktop |
| `status` | `idle`, `busy` or `waiting` (asking something), Claude Code's `shell` (at its prompt while a shell command it ran in the background runs, which says nothing of its agents in the background) taken as `idle`, as it takes your messages; `closed` for a conversation with no process, whose row says "Stopped · press to carry on" |
| `statusUpdatedAt` | when the status last changed; for a terminal session that has ended, when its conversation last moved |
| `alsoOpen` | the conversation's other copies, when it runs in more than one process: each `{entrypoint, paused, busy, hostSessionId}`, `paused` for one stopped in its terminal, `busy` for one at work, and `hostSessionId` for one in Claude Desktop |

## From Claude Desktop

`~/Library/Application Support/Claude/claude-code-sessions/<account>/<org>/local_<id>.json`: one file per
conversation, running or not.

| Field | What it is |
|---|---|
| `activityAt` | when the conversation last did something: Claude's own time, or the hook's (below) when that's later |
| `lastFocusedAt` | when the conversation was last shown in Claude |

A conversation with no process, active in the last three days (or shown in Claude now), gets a row from this file
alone: `sessionId` (the terminal session's id if it was resumed in one), `hostSessionId`, `name` (its title, or
"Untitled"), `cwd`, `entrypoint` `claude-desktop`, `status` `closed`, `pid` 0, and its last activity as both
`statusUpdatedAt` and `activityAt`.

## From Whozmove's record of terminal sessions

`~/Library/Application Support/Whozmove/conversations/<sessionId>.json`: one file per terminal session, written by the
Claude Code module while the session runs (its id, folder, name, the terminal it runs in, its process, its transcript
and when its conversation last moved; no prompts or replies), as Claude Desktop keeps one per conversation. A session
that has ended, whose conversation moved in the last three days, gets a row from this file alone, while Claude Code
still has its transcript and its folder is there, and no other row has it (Claude Desktop's own comes first): its
`sessionId`, `name`, `cwd`, `entrypoint` `cli`, `status` `closed`, `pid` 0, and when its conversation last moved as
`statusUpdatedAt`. A session whose process went on to another conversation (`/clear`, or `/resume` of another) isn't
kept.

| Field | What it is |
|---|---|
| `opensIn` | the terminal a press on its row opens it again in, carrying the conversation on under the same id: the one it ran in while that's on the Mac and Whozmove can open a tab there, else the one New Conversation starts in, else macOS's Terminal |

## From the hook

`~/Library/Application Support/Whozmove/sessions/<sessionId>.json`, written by the hook `whozmove-claude.py`
(modules/claude-code/plugin/hooks/).

| Field | What it is |
|---|---|
| `lastPrompt`, `lastPromptAt` | the last message sent to Claude, and when |
| `promptFrom` | who sent it when it wasn't you: another session, by its name ("Another session" when it gave none), the message alone in `lastPrompt` |
| `promptFromAddress` | that session's address: the messaging socket of the process that sent it |
| `promptFromSession` | that session's id, found the first time the message is read, if the process that sent it ran then and started before it came |
| `lastReply`, `lastReplyAt` | Claude's last reply, and when |
| `notice` | what Claude Code last notified about (waiting for permission, say), until the next prompt or reply |
| `activity`, `activityAt` | the live line: what Claude is doing ("Reading app.ts"), and when that step began (for a Claude Desktop conversation, Claude's own time when that's later) |
| `stageAt` | when the hook last saw a step, a turn or a compaction start or end |
| `outcome`, `outcomeAt` | how far the last turn took the work (`Implemented`, `Tested`, `Committed`, `PR raised`, …), and when |
| `workSteps` | what the current piece of work has been through: `Built`, `Tested`, `Validated` |
| `builtAt` | when a build last succeeded: the panel offers Deploy for a build newer than the last deploy, in the folder the session runs in (where its commands run) |
| `audit` | the last local code review, from its report (Claude Code's ReportFindings tool), and again from its report of what became of each finding: `{found, left, settled, at, branch}`, `branch` the one checked out where the session ran it (for a detached HEAD, its commit's first 7 characters). The work line's start says how it went while there's work to go on that branch: one with nothing left to fix until the checkout is edited again, any other until it's edited after a commit made since the review last reported |
| `workRoot` | the checkout the session last edited files in |
| `editedAt` | when it last edited files there: of the sessions running in a checkout, the one that edited it last speaks for it, and its row has the checkout's numbers and next steps. Edits in another checkout don't move a row, but that checkout's steps and Deploy wait while its agent is on a turn that has edited files there (`editedAt` after `lastPromptAt`) |
| `permissionMode` | the session's permission mode, as of its last event |
| `background` | the jobs Claude still runs in the background once its turn has ended, oldest first, while the session takes your messages: each `{what, command, startedAt, holds, step, stop}`, what the job is (as Claude describes it, else its command), a shell command's command line, when the hook first noted it, `holds` for one that can change files in the session's folder (its agents, workflows and teammates, and any kind Claude Code adds later until it's known), which the next steps and Deploy wait for (a shell command it left running, a dev server say, doesn't: it may run all day), the step an agent among them is on, and what to type in the session to stop it (Claude Code's `/tasks`). The row shows a mark round its dot for each, and a line under Claude's naming them. The hook keeps the list from what Claude Code lists as each turn stops, and between stops from each job's start and each background agent's end; the app leaves out what's plainly over: everything once the session's process has gone, a job last noted before that process started (the earlier process's), a shell command once the session is at its prompt and Claude Code no longer says one runs, a shell command that is wholly one of Whozmove's own waits through its plugin's ask-panel.sh (`wait`, `ticket --wait`), whose row says what it waits on instead (`wait`), an agent whose own record says it has finished, and Claude Code's own housekeeping. Missing when there are none |

## Added by the app

| Field | What it is |
|---|---|
| `git` | the checkout the session runs in, read from its `.git`: `{branch or detached, root, worktree, worktreeOf, mainRoot}` |
| `workGit` | the same for `workRoot`, only for a session that runs outside any checkout: its row is about the one it last edited files in. A session that runs in a checkout is always about that one |
| `checkout` | that checkout's state, from `git status` and `gh`: `{changes, ahead, behind, upstream, remotes, checkedAt, pr, prBranch, prCheckedAt}` (`upstream`: the branch follows one on a remote, as `origin/main`; one that follows a local branch has none, and `ahead` and `behind` are 0 then; `pr` is null when GitHub says the branch has none, or the branch isn't on any of the repo's remotes, so it can't have one, and missing until `gh` has answered), its `base` branch, `baseRef`, the ref it's counted from (GitHub's copy of it, as `origin/main`, else the local one), and `aheadOfBase` (commits the base doesn't have), and `headAt`, when its last commit was made (git's commit time, in seconds). For the next steps: `newFiles` (files git doesn't track yet), and how the changed files split, `filesStaged` (all their changes staged), `filesPartly` (staged, then changed again) and `filesUnstaged` (none staged, or in conflict), which say whether a commit takes only what's staged |
| `prs` | the PRs the session made or worked on, newest first: each `{url, number, repo, at}` from its transcript, and what `gh` says about it: `title, state, isDraft, author, additions, deletions, changedFiles, createdAt, checks, review` and `headRefName` (its branch, which the next steps match against the session's) |
| `messageAt` | when the conversation last moved, from its transcript |
| `agent` | how its agent is set up, at the start of the bottom line: `{mode, model, effort, tokens, window, compactWindow, today}`, `window` being its context window in tokens (1M for Opus and Fable 5.x and `[1m]` models, or once it holds more than 200k, else 200k), which the ring and `compactTime` both go by, `today` being what its replies and its sub-agents' used since midnight (input, cache writes, cache reads and output, each reply once), 0 when none, which the usage card's foot line goes by |
| `ask` | a permission request waiting in the panel, as the permission hook asked it over its line: `{id, sessionId, tool, input, cwd, at, pid}` (`pid` the hook's process, as macOS names it), with `truncated` when its input was cut short to show, `legacy` for one a session started before Whozmove's update left in a file, which the panel doesn't answer, and `expiresAt` when it goes by itself if no one answers it by then (Don't Wait on Me, on for its session; held off while it's being answered, which moves it on), with `waits`, the session's whole wait in ms, which its card counts down. Claude's questions carry `canSayWhy` when the hook can turn them down to chat about them (`clarify`). A plan waiting for your OK is one too (`tool` is `ExitPlanMode`, its `input` has `plan` and `planFilePath`) |
| `writings` | what the session wrote for you to read, from its transcript, newest first (at most 50): each `{id, kind, title, path, at}`. `kind` is `plan` (each time Claude presented a plan for your OK, with `status`: `waiting`, `approved` or `declined`), `prototype` (an `.html` page it created, or published, with its `url`) or `notes` (a `.md` file it created). Files it only rewrote, and Claude Code's own files, aren't listed. What each says is read only when it's opened in the reader |
| `changes` | what isn't committed in the session's checkout, as git status sees it, and the session's own share of it: `{all, known, added, removed, files, parts, complete, v}`. `all` is the checkout's, as git counts it, which the row's numbers show: `{added, removed, files, unstaged: {files, added, removed}, staged: {files, added, removed}}`, every change since the last commit (each file once, new files included), then what `git diff` shows plus the files git doesn't track yet, and what `git diff --cached` shows (a file staged and changed again is in both). The rest is the session's share: the checkout's uncommitted change is read from git, and each changed line is credited to the listed session whose edits (Edit, MultiEdit and Write, from its transcript and its sub-agents' records) put it in or took it out, its shell commands' included (what Claude Code records each one changed, in auto mode); a plain or repeated line (`}`, a blank, a text there twice) goes with the lines around it. `files` are the session's, newest edit first: each `{path, added, removed, edits, at, created, saved, shared}` (`path` within the checkout; `saved`: nothing in it left unstaged; `shared`: someone else changed it too). `parts` is the checkout's uncommitted change by whose its lines are, `{who: [added, removed]}`: a session's id; `outside` (no listed session's record has it: your own, a closed session's, what git brought in); or `short` (a short or repeated line with nothing around it to tell whose it is by). `known` is false while what the session changed isn't known, as it ran a shell command Claude Code didn't record (or recorded only in part): then `added` and `removed` are the whole checkout's, and `files` and `parts` are empty. `complete`: every listed session in the checkout is known, so `outside` is no listed session's. `v` changes when any of it might have. Missing until the checkout has been counted, and while its last `git status` found nothing to commit (`added` and `removed` are 0 while the session has nothing uncommitted there); the lines themselves reach the page only when the changes view asks |
| `backgroundWait` | why the session's next steps and Deploy wait for what it runs in the background, when something there holds them, as the work part words it: "until “Review the native side” is done in the background (type /tasks in the session to stop it sooner)", or how many; Deploy's button says it |
| `compacting` | when the compaction under way began: one sent from the panel, or, while the session runs, any the hook saw start in the last 15 minutes, by itself or asked for, and not end (its record's `compactingAt`, null once it has ended: its end, which `compactedAt` keeps, or Claude's own next step, your message, the turn ending or Claude waiting for you, a second or more after it began). One that began before the panel's own `/compact` had its result was that one, and has ended |
| `noCompact` | `true` when a `/compact` from the panel certainly couldn't go in now, as far as is known without asking its terminal: it has ended, runs in no terminal the panel can type into, is open twice, or a change from the panel is still going into it (`goingIn`, `switchAsk`). The ring doesn't say "Compact now" then |
| `compactTime` | whether now is a natural break to compact it, `{why, kind}`, or missing (the commands module's CompactTime): idle at its prompt with nothing asked or going in, 200k or more in context (100k with a 200k window), not compacted from the panel since its last message, and its work just saved (`saved`), nearly full (`full`, 85%), or nobody on it for an hour (`away`). The ring says "Compact now" then, with `why` in its tip, and Compact at Breaks compacts it by itself at a `saved` or `full` break |
| `compactedFor` | what Compact at Breaks did for it, until its next message: `{at, why, before, after}` once it compacted it, `why` being the break and `after` its size once read; `{at, stopped}` once it stopped part-way, with why; or `{at, failed}` once it didn't go through, with why |
| `compactNote` | why a compaction a module would send can't go in now, `{text, way}`: its words in full ("Compact at Breaks can't: …"), and the words of the Compact card's button past it, or null. The ring's tip says it, and its card opens saying it |
| `onItAt` | when you were last on it, in ms since 1970, worked out as the row is sent (Row.m): on it in Claude, Ghostty or iTerm2 (`seenAt`, `lastFocusedAt`), or writing to it (`lastPromptAt`, unless another session wrote, `promptFrom`). Missing when you never have been. The list's whose-move and Compact at Breaks both go by it |
| `workEditedAt` | when it last edited files where its edits last landed (`workRoot`), worked out by its agent's module from what its hooks recorded (Claude Code's: ClaudeCodeFacts' ClaudeEditedAt): `editedAt`, or, from an older hook that doesn't note when, the end of its last turn that changed something (`outcome`), else 0. Only with `workRoot`. Which session speaks for a checkout, the review's step, and `compactTime` go by it |
| `reload` | a running session that started before Whozmove's hooks went into Claude Code, and runs without them until it reloads its plugins (nothing it did has been recorded since it started), once its first message is sent: `{state}`, `needed`, `waiting` (pressed, for its turn; one that starts working meanwhile is let go, and offered Reload again once it's done), `reloading`, or `byHand` with `why`, `command` and `held` (the panel couldn't type into it, its tab not certain, say, or Claude Code held the reload back, `held`, as its next message would read the whole conversation again: type the command in it yourself). Missing once the panel has reloaded it since it started, or it has recorded anything since it started |
| `switchAsk` | "Switch model?" asked on the row, `{from, to, tokens, never}`: the model it leaves and the one it switches to, how many tokens the conversation holds (or null), and whether Don't ask again is offered. Before `/model` goes to a Claude Desktop conversation whose cache is warm, once Claude's own box asks it there, or while a terminal session's hook (Claude Code's PreModelSwitch) waits for the answer, which then goes to the hook. Gone once it's answered, or the hook stops waiting |
| `goingIn` | a pick from the panel on its way into a terminal session, `{field, value, inTerminal}`, from the moment it's typed until its result: `inTerminal` once no result has come for it (in 2 seconds, or 10 for a model switch the session's hooks ask about in the panel), or once the panel's own "Switch model?" went unanswered and the hook stopped waiting, as Claude Code is asking about it in the terminal (its "Change effort level?", say). Missing while the panel itself asks "Switch model?" (`switchAsk`), once the command has its result or is given up on, and on a row whose session has ended |
| `focused` | `true` for the session you're on: the conversation Claude Desktop shows now, or the session in the tab a terminal shows (Ghostty or iTerm2), whichever was in front last. Claude Desktop's stays while the terminal's tab holds none of the sessions listed, and while it can't be told which one it holds, the mark stays where it was |
| `seenAt` | when you were last looking at the session: on it for 2 seconds or more, in Claude Desktop, Ghostty or iTerm2 in front, while at the Mac (the screen awake and unlocked, the keyboard or the mouse used in the last 5 minutes). A reply from before then counts as read. Missing until you've looked at it since the app started |
| `team` | its place in the team the session leading it keeps, from `team/team.json` in Whozmove's folder ([team.md](team.md)), read again whenever the file changes: `{role, name}`, `role` being `front` (the session you talk to, when the file names one apart from the session leading the team, with `shown` when the file gives it a name to show), `lead` (the session leading it, with `group`, `groupAt` and `tag` as a member's when the file gives them while it isn't the chief), `member` (with its `part`, with `group` and `groupAt` when the file puts it in a group: the group's name, and its place among the team's groups, or `groupAt` alone, Team's place, when it's in none and the file's `groups` names Team, with `tag` when the file gives it one, a few words shown after its name, and with `shown` when the file gives it a name to show), or `followed` (one of your own sessions it follows). The one marked Chief has `chief: true`: the front, else the lead. A member is the session holding its seat in its own workspace, the folder recorded for it alone ([team.md](team.md#how-sessions-are-matched)): the session the file records while it runs there, else the one that held the seat, or a new conversation on its process, else the one opened first; and while none runs there, its last conversation there, ended: the one that held the seat, else the one the file records, else the one that moved last (one of yours counts by its id, in any folder). A member or one of yours has `job`, the job it's on, when one is under way: `{id, title, steps, at, you, waits, short, ask, priority, holds, stageAt}`, its steps in order, each `{id, word, you, kind, waits}` (`kind`, on a step that waits on you, what it asks of you in One Task's words, when the file gives one; `waits`, on one that doesn't, that nobody works on the job there while it waits its turn), the one it's at, whether that one waits on you, whether it waits its turn (`waits`, only when it does), what's wanted of you then in a few words (`short`) and in full (its `ask`, else its `decision`), how pressing it is (`critical`, `p0`, `p1` or `p2`), and how many jobs under way wait for it (the one being worked on first, else the one that moved last); and, while it's on one being worked on and another of its jobs under way waits on you, `alsoAsks`, `{job, title, short, at, priority, kind}`, that one's id and title, what's wanted of you in a few words (else its step's word), the step it's at, how pressing it is and, when its step says, what it asks of you in One Task's words (of several, the one that moved last). Each also has `status`, where the job its row speaks for stands, when it has one not done or dropped: `{stage, word, words, job, title, stageAt, you}`, `stage` being `work` (under way), `waiting` (under way, at a step that waits its turn, `word` being that step's), `queued` or `parked`, `words` the file's `status` for it, else its `short`, its id and title, when it got there, and whether its step waits on you (one under way first, else one waiting its turn, else the next queued, else the parked one that moved last); or, when the file says what a member is busy with apart from its jobs, `{stage: work, words, doing}`, that and the word for it. The lead has `leads`, the ids of the sessions it leads, A to Z, when it has any: its members', each that has its place on its team (never one of your own it follows, nor one the file gives a place first elsewhere), each the session on that member's row (holding its seat, or ended there standing for it), else the one the file records, so a feature acting on a team reads who's on it from here alone; and `counts`, `{waiting: {critical, p0, p1, p2}, working}`: the jobs under way (at any stage but `queued`, `parked`, `done` or `dropped`) whose step waits on you, by priority, and the rest but those at a step that waits its turn; and `next` while it names what's next for you, `{short, ask, priority, job, title, for}`: that in a few words (its ask when the file gives no short), in full, how pressing it is (its own, else its job's), the job it's for, by id and title, when the file has it, and `for`, the session of the member whose job it is, the one on its row; and `queue` while the file names picks for you, in its order, at most 100: each `{id, job, title, priority}`, the id of a pick it sent One Task itself ([task.md](task.md)), the job it's for by id and title when the file has it, and how pressing that job is (`p1` without one), with no task and no member: One Task keeps those as the pick was checked. Another session open where one of the team works has `{inFolderOf}`, that one's name, and `history: true` when a conversation that has ended there is the team's history rather than yours (a member's own workspace always; the lead's or the front's folder unless it's the project's own, where your own conversations are too); one running in a member's own workspace while another holds its seat also has `duplicate: true`, `earlier` (whether it was opened before the one holding the seat) and, when that one has a name, `seat`, its name. Missing for every other session, and for all of them without the file |
| `answeredFor` | what a session you allow last answered for you on this session's behalf, from its mode menu's May Send Back Plans, May Answer Questions or May Approve Plans: `{by, what, title, note, state, at}`, the name of the session that answered, `sentBack` (this session's plan, sent back with a note), `answered` (its questions) or `approved` (its plan, with `state` `pending` until its transcript's result says `approved`, or `notTaken` if it doesn't within 15 seconds), the plan's title or the first question, the note or each question with what was picked, and when. Kept in the panel's memory, its card shows for 30 minutes, under the chat while nothing else waits there, or until the session asks something newer; missing otherwise |
| `ticket` | the ticket it works on, from a ticket tracker (Jira), given by your press: Start on the new conversation card with the ticket on it, or Use It on its row (the tickets module). `{bound, offer, move, draft, creating}`, each only when there is one. `bound` is the ticket as last read, `{tracker, site, key, link, id, title, type, state, parent, groups, priority, assignee, steps}` (`state` its `{name, kind}`, `kind` one of `todo`, `doing`, `done` or `dropped`; `parent` `{key, title, type}`; `groups` its project and boards, each `{id, name, kind, sprint}`; `steps` its next steps, each `{id, name, to, needs}`, `to` a state, `needs` the fields it asks for, each `{id, name, kind, required, many, options}`), only `tracker`, `site`, `key` and `link` until it's first read; `link` made from its site and key, never taken from what the tracker sends; with `readAt` once read, `reading` while it's first read, and `problem`, `{kind, why, retryAt}`, when the last read didn't read it (`kind` one of `signIn`, `allow`, while macOS asks before it gives this build the sign-in, `slow`, with when to try again, or `failed`); `moved`, its last move, `{to, by, at}` (`by` `itself` or `you`), or `{gone, at}`, with why, when its step had gone by the time of your Move It, until it's next read; and `stopped`, the steps the session marked as a person's, `{step id: why}`, until a read no longer lists them or the ticket moves. `offer` is a ticket waiting on its row for your Use It, `{tracker, site, key, link, instead, again, title, type, state, problem}` (`title`, `type` and `state` as `bound`'s, once the offered ticket is read, which happens once, as it's offered;
